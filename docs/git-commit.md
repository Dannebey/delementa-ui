# Руководство по оформлению коммитов

Данный документ описывает правила и лучшие практики по написанию сообщений коммитов в рамках проекта. Соблюдение этих правил упрощает чтение истории изменений, поиск нужных фиксов или фич, а также автоматизацию процессов (релизы, генерация CHANGELOG и т. д.).

## Зачем нужны правила для коммитов

1. **Улучшение читаемости истории**  
   Когда все коммиты оформлены в едином стиле, легко быстро понять, что было сделано, даже без просмотра диффов.
2. **Автоматизация**  
   Инструменты, такие как [commitlint](https://github.com/conventional-changelog/commitlint), [semantic-release](https://github.com/semantic-release/semantic-release) и другие, могут использовать формат сообщений для определения версии релиза, генерации CHANGELOG и пр.
3. **Упрощение командной работы**  
   Каждый участник команды сразу видит, к какой области относится коммит (фикс бага, новая фича, документация и т. д.).

## Общий формат (Conventional Commits)

Чаще всего используют спецификацию [Conventional Commits](https://www.conventionalcommits.org/). Пример базового шаблона:

**Расшифровка:**
- `<type>` — тип изменений. Например: `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`, `build`, `perf`, `revert`.
- `<scope>` *(опционально)* — область кода, которую затрагивает коммит (например, название компонента, модуля, директории).
- `<subject>` — короткое описание, отвечающее на вопрос «Что сделано?».

### Примеры

- `feat(Button): добавлен новый проп "size"`
- `fix(Input): исправлен баг с фокусом`
- `docs: добавлена документация по структуре проекта`
- `style: форматирование кода по правилам ESLint`
- `refactor(hooks): оптимизирована логика useDebounce`
- `test(Button): добавлены тесты для состояния disabled`
- `chore: обновлены зависимости`

### Расширенный формат коммита

Если нужно добавить более подробное описание, используют следующую структуру:


1. Header (первая строка):
* type(scope): subject
* Не более ~72 символов для <subject> (рекомендуется).
2. Body (опционально):
* Более подробное описание, если в заголовке не поместилось всё нужное.
* Расскажите, зачем был сделан этот коммит, какие детали важны для понимания.
3. Footer (опционально):
* Используется для упоминания задач (например, Closes #123) или других важных заметок (например, BREAKING CHANGE: описание...).

Пример расширенного коммита:

feat(Button): добавлен новый проп "size"

Добавил проп `size`, который позволяет задавать три размера кнопки:
- small
- medium
- large

Closes #42

Типы коммитов (type)

Ниже список часто используемых типов коммитов в соответствии с Conventional Commits:
1. feat — добавление новой функциональности (фичи).
2. fix — исправление бага.
3. docs — изменения только в документации (например, README, MD-файлы).
4. style — правки, не влияющие на код (пробелы, форматирование, точки с запятой и т. д.).
5. refactor — правки кода без исправления багов и добавления фич (улучшение структуры, оптимизация).
6. test — добавление или обновление тестов.
7. chore — изменения в процессах сборки, настройках, зависимости и т. п. (не затрагивают исходный код приложения).
8. build — изменения, влияющие на систему сборки или внешние зависимости (например, Webpack, Rollup).
9. perf — изменения, направленные на улучшение производительности.
10. revert — откат кода к предыдущему состоянию.

Scope (область)
•	scope уточняет, к какой части проекта относится коммит.
Примеры: Button, Input, docs, hooks, styles, lint, deps.
•	Можно не указывать scope, если она не несёт пользы.


Примеры правильных сообщений
* feat(Button): добавлен вариант outline
* fix(Input): исправлен баг с валидацией
* docs: обновлен README по структуре проекта
* refactor: переименование переменных для лучшей читабельности
* test(Button): добавлены тесты для различных состояний
* chore(deps): обновлен eslint до версии 8.0.0

Примеры неправильных сообщений

* fix: что-то починил (непонятно, что именно и в каком модуле)
* commit: done (отсутствует тип, не ясно, что изменилось)
* update code (слишком общее и не соответствует формату)

Резюме
1. Соблюдайте формат type(scope): subject.
2. Делайте заголовок сообщения информативным, но не слишком длинным.
3. При необходимости добавляйте описание в тело (body).
4. Используйте footer для ссылки на задачи, PR, тикеты (например, Closes #123).
5. Подключите commitlint и Husky, чтобы автоматизировать проверку сообщений коммитов.

Следование этим правилам упростит командную работу и сделает историю изменений понятной и удобной.
